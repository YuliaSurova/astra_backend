# Обоснование архитектурных решений

## 1. Выбор СУБД: SQLite по умолчанию, PostgreSQL как опция

**Задача:** данные должны загружаться в БД, при этом проект должен легко открываться на любом компьютере.

**Решение:** по умолчанию используется SQLite (файловая БД, встроена в Python), а код готов к работе с PostgreSQL через строку подключения `DATABASE_URL`.

**Обоснование:**
- SQLite не требует установки и настройки сервера — база создаётся автоматически при запуске пайплайна. Это гарантирует, что проект заработает у любого человека: достаточно клонировать репозиторий, установить зависимости и запустить пайплайн;
- объём данных (340 тыс. строк) SQLite обрабатывает без проблем;
- PostgreSQL оставлен как опция для случаев, когда нужен многопользовательский доступ или более мощная аналитика (оконные функции, расширение TimescaleDB для временных рядов);
- переключение между СУБД не требует изменения кода — меняется только строка подключения.

## 2. Схема «звезда» и нормализация

**Задача:** устранить избыточность данных и обеспечить целостность.

**Решение:** три таблицы:
- `macro_drivers_weekly` — измерение (одна строка на неделю);
- `building_materials_transactions` — фактовая таблица;
- `data_dictionary` — словарь данных (метаданные).

**Обоснование:**
- в исходном CSV транзакций три экзогенных макро-столбца (`housing_starts_index`, `lumber_price_index`, `mortgage_rate`) продублированы в каждой из 340 000 строк, хотя уникальных комбинаций всего 313 (по числу недель). Вынос их в справочник устраняет ~99,9 % дублирования, экономит место и исключает аномалии обновления: при изменении показателя за неделю обновляется одна строка справочника, а не тысячи строк фактов;
- внешний ключ `date → week` гарантирует ссылочную целостность: транзакция не может ссылаться на несуществующую неделю;
- схема «звезда» удобна для аналитики: соединение фактов с измерением даёт полный контекст (макрофакторы и сезонность) для каждой транзакции.

## 3. SQLAlchemy Core вместо чистого SQL или ORM

**Задача:** схема и вставка должны работать одинаково в SQLite и PostgreSQL.

**Решение:** SQLAlchemy Core (таблицы через `Table`/`Column`, `MetaData`).

**Обоснование:**
- SQLAlchemy генерирует DDL под конкретную СУБД (типы, автоинкремент, ограничения), поэтому один и тот же код работает и с SQLite, и с PostgreSQL;
- Core легче и прозрачнее, чем полноценный ORM: для пайплайна загрузки не нужны объекты-модели, достаточно таблиц и вставок;
- `metadata.create_all()` / `drop_all()` автоматически учитывают порядок зависимостей таблиц (внешние ключи).

## 4. Диалектозависимый суррогатный ключ

**Задача:** автоинкрементный первичный ключ в обеих СУБД.

**Решение:** `BigInteger().with_variant(Integer, "sqlite")`.

**Обоснование:** в SQLite автоинкремент работает только для типа `INTEGER PRIMARY KEY`, а в PostgreSQL предпочтителен `BIGINT`. `with_variant` позволяет использовать один тип в коде, а в каждой СУБД получать корректный DDL. Без этого трюка вставка в SQLite падала с ошибкой `NOT NULL constraint failed` (это было обнаружено при тестировании и исправлено).

## 5. Проверка целостности до загрузки

**Задача:** не допустить попадание «грязных» данных в БД.

**Решение:** функция `validate_fk()` проверяет, что каждая дата транзакции присутствует в справочнике макроэкономики, ещё до вставки.

**Обоснование:**
- ошибка обнаруживается на раннем этапе, с понятным сообщением (какие недели отсутствуют), а не в середине загрузки;
- это «шлюз качества»: пайплайн останавливается, если данные неполные или несогласованные;
- дополнительно внешний ключ в БД защищает от нарушений на уровне самой СУБД.

## 6. Стратегия вставки: COPY для PostgreSQL, executemany для SQLite

**Задача:** загрузить 340 тыс. строк быстро и без переполнения памяти.

**Решение:** функция `bulk_insert()` выбирает стратегию по диалекту: `COPY` (PostgreSQL) или пакетная вставка по 10 000 строк (SQLite и другие).

**Обоснование:**
- `COPY` — самый быстрый способ массовой загрузки в PostgreSQL (одна операция вместо тысяч отдельных INSERT);
- пакетная вставка чанками не держит все данные в памяти одновременно и работает в любой СУБД;
- `NaN` заменяется на `None` (корректный NULL), чтобы не было ошибок типов.

## 7. Включение внешних ключей в SQLite

**Задача:** ограничение `date → week` должно работать и в SQLite.

**Решение:** обработчик события `connect` выполняет `PRAGMA foreign_keys=ON`.

**Обоснование:** в SQLite внешние ключи выключены по умолчанию — без этого ограничение существует только «на бумаге», и нарушающие вставки не отклоняются.

## 8. Идемпотентность и защита от дублей

**Задача:** повторный запуск не должен создавать дубликаты.

**Решение:** перед загрузкой проверяется, есть ли уже данные в таблицах; при повторном запуске без флага `--reset` пайплайн останавливается с подсказкой. Флаг `--reset` пересоздаёт схему.

**Обоснование:** это делает пайплайн безопасным для повторных запусков и понятным для пользователя.

## 9. Структура пакета и разделение ответственности

**Задача:** код должен быть читаемым и расширяемым.

**Решение:** пакет `pipeline/` с модулями: `config.py` (настройки), `db.py` (схема), `load.py` (логика), `run.py` (CLI).

**Обоснование:**
- каждый модуль отвечает за свою часть: конфигурация, схема, логика, запуск — это упрощает тестирование и изменение;
- точка входа `run.py` отделена от логики, поэтому пайплайн можно вызывать и как библиотеку (`from pipeline.load import run_pipeline`), и из командной строки;
- конфигурация через переменные окружения позволяет менять настройки без правки кода.

## 10. Исключение базы из Git

**Задача:** база не должна попадать в репозиторий.

**Решение:** `astra.db` добавлен в `.gitignore`.

**Обоснование:** база генерируется автоматически при запуске пайплайна, поэтому хранить её в Git бессмысленно (она раздувает репозиторий и создаёт конфликты). Это же обеспечивает переносимость: на другом компьютере база создастся заново из CSV-файлов, которые лежат в репозитории.
